FOCUS: - Decomposition: break a problem into inputs, transformations, outputs
FOCUS: - Data flow: where data comes from, how it changes, where it lands
FOCUS: - Data modeling: grain (what one row means), keys, joins, one-to-many traps
FOCUS: - Control flow: conditions, loops, "for each group, do X"
FOCUS: - Failure modes: bad data, nulls, duplicates, schema changes
FOCUS: - Testing and verification: invariants, row counts, reconciliation
FOCUS: - State and idempotency: what happens if it runs twice or fails halfway
FOCUS: - Separation of concerns: config vs. logic vs. I/O
FOCUS: - Library awareness: what exists and the trade-offs
FOCUS: - Code reading: spotting silent bugs in AI-written code
FOCUS: Where each concept is usually covered best (starting points; check each book's table of contents):

FOCUS: - Data flow: Fundamentals of Data Engineering; Data Pipelines Pocket Reference
FOCUS: - Data modeling: The Data Warehouse Toolkit
FOCUS: - Control flow (for each group, do X): Python Data Science Handbook
FOCUS: - Failure modes, state and idempotency: Designing Data-Intensive Applications; Data Pipelines Pocket Reference
FOCUS: - Separation of concerns: A Philosophy of Software Design
FOCUS: - Library awareness: Python Data Science Handbook
FOCUS: - Diagrams: c4model.com and the Mermaid documentation
FOCUS: - Testing and code reading: no book covers them well; teach them with exercises on my datasets
FOCUS: Practice rules, applied in the hands-on step and the mini-project of every part:
FOCUS: 1. Draw before you build. Before any code, ask me to draw the system as a Mermaid diagram (text), using the type that answers the question of the part: data flow diagram (sources, steps, outputs), ER diagram (tables, keys, grain, relationships), flowchart (decisions and branches), sequence diagram (which component calls which, in what order), or C4 model (the system at 3 or 4 zoom levels). Critique my diagram, then let me fix it.
FOCUS: 2. Mark the failure points on every diagram (bad data, nulls, duplicates, schema change, a step that runs twice or stops halfway) and say which check would catch each one.
FOCUS: 3. Only after the diagram is agreed, give me the code skeleton, and make me verify it with invariants: row counts, key uniqueness, totals that must reconcile.
FOCUS: 4. Code reading: from time to time show me a short, plausible script, the kind an AI would write, with one or two silent bugs (for example a join that multiplies rows, or nulls dropped without warning). Let me find them before you reveal them.
FOCUS: Use my datasets from the Project for every example.
